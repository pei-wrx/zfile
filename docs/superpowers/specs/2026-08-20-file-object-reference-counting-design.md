# 文件物理对象引用计数设计

## 目标

将文件节点和物理存储对象拆分，使相同 SHA-256 的文件只保存一份物理文件。每个文件节点持有一个 `file_object_id` 引用；节点永久删除时减少引用计数，只有计数归零才删除物理对象和磁盘文件。

## 数据模型

新增 `file_objects` 表，保存物理对象的最小字段：

- `id`
- `checksum`：SHA-256，唯一
- `size_bytes`
- `content_type`
- `storage_key`
- `reference_count`
- `created_at`、`updated_at`

`file_nodes` 新增 nullable 的 `file_object_id`。现有 `storage_key`、`checksum` 字段在迁移后保留为兼容影子字段，供历史迁移清理使用；业务代码不再依赖它们。`content_type` 和 `size_bytes` 继续保留在节点上，因为 MIME 类型可能因节点名称/扩展名不同而不同，目录节点也需要 `size_bytes=0`。

## 迁移策略

Flyway 新增迁移：

1. 创建 `file_objects`。
2. 为非空 checksum 的历史文件按 checksum 合并对象，选择稳定的最小 storage key 作为规范物理文件，引用计数为对应节点数。
3. 为 checksum 为空的历史文件按 storage key 建立独立对象，避免错误合并并保证可读取。
4. 给历史文件节点回填 `file_object_id`，删除 `file_nodes.storage_key` 的唯一索引以允许多个节点引用同一对象。

应用启动后扫描已迁移节点和规范对象，删除已确认不再作为规范对象使用的历史重复 storage key。清理过程只处理 `file_object_id` 非空的节点，并在对象表为空时跳过，保证迁移异常不会误删文件。

## 业务流程

- 普通上传：后端临时落盘并计算 SHA-256；若对象已存在则删除临时文件并增加引用，否则将临时文件提交为新对象；随后创建节点。
- 上传预检命中：增加对象引用并创建节点，不进行物理复制。
- 节点复制：复制目录树时复用每个文件节点的对象引用，不复制物理文件；事务失败时数据库回滚引用计数。
- 回收站：移入和恢复不改变引用计数；永久删除/清空回收站按被删文件节点聚合减少引用，事务提交后删除归零对象的物理文件。
- 下载、预览和分享：先通过 `file_object_id` 查询对象，再使用对象的 storage key 加载流；下载次数逻辑保持不变。

用户配额仍按文件节点的逻辑大小计算，因此同一物理对象被多个用户引用时，每个用户仍占用对应逻辑空间。

## 错误处理与并发

对象引用增加/减少使用带条件的数据库更新，禁止引用计数变为负数。对象表以 checksum 唯一约束防止并发上传产生重复对象；上传竞争时临时对象会被删除并转为引用已有对象。数据库事务回滚只回滚节点和引用计数，物理文件清理由事务回调处理。

## 验证范围

- 预检命中只增加引用，不调用物理复制。
- 普通上传命中已有对象时不产生第二份物理对象。
- 节点复制复用对象并增加引用。
- 两个节点永久删除时第一次删除不删物理文件，最后一次删除才删。
- Flyway 迁移 SQL 可解析，完整 Maven 测试和两份前端构建通过。
